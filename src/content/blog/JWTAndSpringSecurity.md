## How the JWT signature is generated?

A JSON Web Token (JWT) signature is generated by passing the encoded header, the encoded payload, and a secret key or private key into a cryptographic algorithm specified in the header.

### Steps to Generate a JWT Signature
* **Encode the Header:** Convert your JSON header (containing the algorithm type like *HS256* and token type JWT) into a Base64URL-encoded string.
* **Encode the Payload:** Convert your JSON payload (containing your claims or user data) into a *Base64URL-encoded* string.
* **Create the Signing Input:** Combine the encoded header and the encoded payload with a period character (.) separator:BASE64URL(Header) + "." + BASE64URL(Payload)
* **Apply the Cryptographic Algorithm:** Run the combined signing input through the algorithm declared in your header (such as *HMAC-SHA256*) using a server-side secret key (for symmetric algorithms like *HS256*) or a private key (for asymmetric algorithms like *RS256*).
* **Encode the Signature:** Base64URL-encode the resulting signature output and append it as the third segment of the final token:BASE64URL(Header) + "." + BASE64URL(Payload) + "." + BASE64URL(Signature)

### The Two Main Algorithm Categories
* **Symmetric Algorithms:** Use a secret key (for example, *HS256* or *HS384* or *HS512*). The same key is used for both signing and verification.
* **Asymmetric Algorithms:** Use a private key for signing and a public key for verification (for example, *RS256* or *ES256*).


| Feature             | Symmetric                                                                     | Asymmetric                                                                     |
|---------------------|-------------------------------------------------------------------------------|--------------------------------------------------------------------------------|
| Key Type            | Single Shared Secret String                                                   | Public / Private Key Pair                                                      |
| Security Risk       | High if shared. Anyone who can verify the token can also forge a valid token. | Low. Public keys can be exposed safely; only the auth server can forge tokens. |
| Performance         | Very Fast. Cryptographically lightweight.                                     | Slower. Requires complex mathematical operations.                              |
| Key Management      | Difficult to securely share across multiple independent microservices.        | Easy. Public keys can be exposed via a public URL endpoint (JWKS).             |
| Ideal Architecture  | Monoliths, small single-server APIs.                                          | Distributed microservices, APIs with third-party consumers.                    |

## How signature verification works in JWT?

JWT signature verification works by recalculating the cryptographic signature on the server using the received header, payload, and a secret key or public key, then comparing it to the signature attached to the token.

### How the Verification Process Works

* **Extract parts:** The server splits the incoming JWT string by dots (.) into three parts: the encoded header, the encoded payload, and the signature.
* **Read the header:** The server decodes the header to check the signing algorithm (alg) specified inside it (such as HS256 or RS256).
* **Recreate the signature:** The server takes the encoded header and encoded payload strings from the token, combines them with a dot, and runs the same hashing or cryptographic algorithm using its stored secret key (for symmetric signing) or public key (for asymmetric signing).
* **Compare signatures:** The server compares its newly generated signature with the signature provided in the third part of the token.
* **Determine validity:** If both signatures match completely, the server confirms that the data has not been tampered with in transit and trusts the contents. If they do not match, the token is rejected immediately.

## Detecting Payload Tampering in JWT?

JSON Web Token (JWT) payload tampering is detected through cryptographic signature verification.

### How Detection Works

* Signature Derivation: When a server creates a JWT, it generates a signature by hashing the encoded header and payload using a secret key or private key.
* Re-computation: When a client sends the JWT back, the server decodes the token, extracts the algorithm specified in the header, and re-computes the signature using the original header, payload, and its stored secret key.
* Comparison: The server compares the computed signature with the one provided in the token. If they match, the payload is trusted; if they don't match, the token is rejected.

> #### Refresh Token Rotation
>* Single-use tokens: Configure your authorization server to issue a brand-new refresh token every time the old one is used to get a new access token.
>* Reuse detection: If an attacker tries to use an already rotated, old refresh token (while the legitimate user is also active), the server flags a security violation.
>* Family revocation: The system immediately invalidates the entire chain or family of tokens, locking out both the user and the hacker.
>#### Cryptographic Token Binding
>* Device binding: Tie tokens to a specific device using standards like DPoP (Demonstrating Proof-of-Possession) or mTLS (Mutual TLS).
>* Key requirement: The client must present a private cryptographic key that matches the public key embedded in the token during every request.
>* Prevention of replay: Even if an attacker copies the tokens, they cannot use them from a different machine or IP without possessing the bound private key.
>#### Contextual and Behavioral Monitoring
>* Anomaly detection: Monitor for sudden shifts in IP address, geographic location, or User-Agent/device fingerprint during a session.
>* Continuous Access Evaluation (CAE): Revoke access tokens near-instantly when critical network or security events change rather than waiting up to an hour for natural expiration.
>#### Short Lifespans and Secure Storage
>* Short access duration: Keep access token validity very brief (5 to 15 minutes) so that a stolen access token has a tiny window of usefulness.
>* HttpOnly cookies: Store refresh tokens in secure, HttpOnly, SameSite cookies instead of client-side localStorage to reduce the risk of theft via Cross-Site Scripting (XSS).

## How JWT authentication filters works?

* Intercept: The filter looks at every incoming web request before it reaches your main application logic or controllers.
* Extract: It reads the Authorization header from the request and looks for a token starting with the word Bearer.
* Validate: It checks if the token signature is real, makes sure it has not expired, and verifies details like the issuer.
* Authenticate: If the token is good, it pulls user details (like username and roles) from the token and saves them into the security holder system so the app knows who is visiting.
* Proceed: It lets the request move forward down the chain of filters to the controller.


## What is securitycontextholder in spring boot?

In Spring Boot and Spring Security, the SecurityContextHolder is a central utility class that serves as the entry point for accessing the details of the currently authenticated user. It essentially acts as a container or "locker" that provides access to the application's current security context

### The Core Architecture Breakdown

```text
SecurityContextHolder
   └── SecurityContext
          └── Authentication
                 ├── Principal (The User details)
                 ├── Credentials (Password / Token - usually cleared after login)
                 └── Authorities (Roles and Permissions)

```

* SecurityContextHolder: The helper class providing static methods to access the SecurityContext.
* SecurityContext: Holds the Authentication object.
* Authentication: Represents the logged-in user, containing their Principal (identity), Credentials (proof), and Authorities (granted permissions like ROLE_ADMIN)

### How It Works Internally?

1. ThreadLocal Storage (Default): By default, SecurityContextHolder uses a ThreadLocal strategy to store these details. This means the user's security data is bound strictly to the current execution thread handling the HTTP request. Because of this, you can access user details anywhere in your code (Service, Controller, Repository) without explicitly passing it around as a method argument.
2. The Lifecycle: When a user logs in, Spring Security's filter chain handles the authentication, populates the Authentication object, and sets it in the holder. Once the request finishes, Spring Security automatically clears the context to prevent memory leaks or security leaks between threads.

### Different Storage Strategies?

While ThreadLocal is the default behavior, SecurityContextHolder can be configured to use different strategies depending on your application structure:

* MODE_THREADLOCAL (Default): Tied to a single thread. Perfect for traditional web applications.
* MODE_INHERITABLETHREADLOCAL: Allows child threads spawned from a secure thread to inherit the same security context. Useful if you use @Async methods.
* MODE_GLOBAL: All threads in the JVM share the same context. Used primarily for standalone desktop applications (like a Swing or JavaFX app).

### What is authentication object?

In Spring Security, the Authentication object is a core interface that represents the identity and request token of a user or client interacting with the application. It acts as a container for all security-related information about the current user, playing a double role as the initial credentials input during a login attempt and the final secure identity output once the user is successfully validated.

#### The Two Phases of the Authentication Object

The Authentication object behaves differently depending on where it is in the security workflow:
1. Pre-Authentication (The Request): When a user attempts to log in, Spring Security packages their raw input (like a username and password or a JWT token) into an unauthenticated Authentication object. At this stage, its isAuthenticated() property is set to false.
2. Post-Authentication (The Result): The AuthenticationManager validates the credentials. If successful, it replaces the unauthenticated object with a fully populated, trusted Authentication object where isAuthenticated() is true. This final object is then stored in the thread-local SecurityContext.

#### Key Components of the Authentication Object

The Authentication interface includes several essential methods to fetch the user's security blueprint:

* getPrincipal(): Returns the user's principal (like username or email)
* getCredentials(): Returns the credentials (password or token)
* getAuthorities(): Returns the user's granted authorities (roles and permissions)
* isAuthenticated(): Returns true if the user is authenticated

## Comparison: Gateway vs. Downstream Authentication

| Feature                   | Authentication at API Gateway                                                 | Authentication at Downstream Services                                     |
|---------------------------|-------------------------------------------------------------------------------|---------------------------------------------------------------------------|
| Code Duplication          | Low Consolidates auth logic into a single component                           | High. Each service needs its own auth stack/boilerplate.                  |
| Performance               | High. Tokens are validated once at the perimeter.                             | Lower. Multiple internal calls cause redundant cryptographic validations. |
| Attack Surface            | Narrow. Unauthenticated requests are rejected immediately at the edge         | Wide. Unauthenticated requests travel deep into the internal network.     |
| Blast Radius (Compromise) | High. If the gateway is breached, the entire internal system can be exposed.  | Low. A breach in one service doesn't automatically compromise others.     |
| Coupling                  | Low. Downstream services remain completely unaware of the identity provider.  | High. Downstream services must align with the auth server/token format.   |
